# รีวิว Financial Rules v0.1 เทียบกับโค้ดปัจจุบัน

วันที่รีวิว: 2026-10-14 · โค้ดที่รีวิว: commit `aa3e0f9` · ผู้รีวิว: Claude (ฝั่ง Member 1)
สถานะ: **รีวิวอย่างเดียว ยังไม่ได้แก้โค้ดส่วนการเงิน** รอทีมเศรษฐศาสตร์ตัดสินใจตามข้อ 3 ก่อน

ตัวเลขตัวอย่างทั้งหมดในเอกสารนี้ได้จากการรันโค้ดจริงบน `data/synthetic/profile_demo.yaml`

## 1. สรุปผล

| กฎ | สถานะ | สรุปสั้น |
|---|---|---|
| 1. Available Cash | **Partially Implemented** | คำนวณถูกและไม่นับซ้ำ แต่ไม่มีตัวเลข "available cash" ตัวเดียวตามนิยามของกฎ และการจัดการ deficit ต่างจากกฎ |

**Needs Economics Decision** มี 9 ข้อ รวมไว้ที่ข้อ 3

## 2. รายละเอียดรายกฎ

### กฎ 1: Available Cash

**Implemented**
- รายได้, ค่าใช้จ่ายจำเป็น, หนี้ขั้นต่ำ และค่าใช้จ่ายยืดหยุ่น ถูกหักตามวันที่จริงใน `lifecfo/cashflow/forecast.py`
- เงินสดที่มีอยู่ (ซอง `UNALLOCATED`) ถูกรวมเป็นยอดยกมา
- กันนับซ้ำด้วย envelope model: เงินสำรองกับเงินออมเป้าหมายอยู่คนละซอง การโอนเข้าซองไม่เปลี่ยนเงินสดรวม มี test ยืนยัน (`test_total_cash_changes_only_by_income_and_spending`)
- เมื่อจ่ายของจำเป็นไม่ได้ ระบบไม่สร้างแผน และรายงานยอดที่ขาดแทน (`ESSENTIAL_SHORTFALL`)

**ต่างจากกฎ**
- **ไม่มีตัวเลข available cash ตามนิยามของกฎ** ตัวที่ใกล้ที่สุดคือ `free_cash_per_month_after_essentials` ใน agent tool ซึ่งเท่ากับ รายได้ − จำเป็น − หนี้ขั้นต่ำ = 12,000 แต่ **ยังไม่ได้หัก flexible** ตามกฎควรเป็น 12,000 − 3,000 = 9,000
- **การจัดการ deficit ต่างจากกฎ** กฎบอกว่าถ้างบติดลบให้แจ้ง deficit แทนการสร้างแผนปกติ แต่ตอนนี้ optimizer มองว่า flexible ตัดได้ถึงขั้นต่ำ (`min_amount`) ถ้าตัดแล้วพอ ระบบจะสร้างแผนให้เลย เช่นรายได้ลด 20% ระบบตัด leisure จาก 3,000 เหลือ 1,000 แล้วออกแผน โดยไม่ได้แจ้งแยกว่า "ตามงบเดิมติดลบ 6,000 ต่อเดือน"
- **ไม่มี buffer เงินสด** เงิน unallocated ที่มีอยู่ถูกกวาดเข้าเป้าทั้งหมดในเดือนแรก เช่นถ้ามีเงินสด 25,000 แผน Goal First โอน 34,000 ในเดือนแรกจนเหลือ 0 (ยังจ่ายบิลได้ครบเพราะระบบตรวจรายวัน แต่ไม่มีกันชน)

### กฎ 2: Emergency Fund

**Implemented**
- gap = เป้า − ยอดปัจจุบัน และถูกใช้เป็นเพดานกับตัวถ่วงน้ำหนักใน optimizer

**Missing**
- เป้าเงินสำรองเป็นตัวเลขที่กรอกเองต่อโปรไฟล์ (`reserve_target_thb`, demo ใช้ 20,000) ไม่ได้คำนวณจากค่าใช้จ่ายจำเป็น
- ถ้าใช้กฎ 3 เดือน เป้าของ demo จะเป็น 3 × 18,000 = **54,000** แทน 20,000 ซึ่งจะเปลี่ยนผลของทุกแผนอย่างมาก (เงินสำรองจะใช้เวลานานขึ้นหลายเท่า และเป้าอื่นจะช้าลง)

### กฎ 3: Debt Management

**Implemented**
- หนี้ขั้นต่ำเป็น hard constraint จ่ายก่อนจัดสรรให้เป้าใด ๆ ทั้งใน forecast และ optimizer
- หยุดจ่ายเมื่อยอดหนี้หมด มี test ยืนยัน

**Missing**
- **APR ถูกเก็บไว้แต่ไม่ถูกใช้ในการคำนวณใดเลย** ไม่มีการคิดดอกเบี้ย ยอดหนี้จึงลดเร็วกว่าความจริง (เขียนเป็นสมมติฐาน A5 ไว้ใน `FINANCIAL_MODEL.md`)
- **ยังไม่มีการจ่ายหนี้เพิ่ม** optimizer ไม่มีตัวแปรสำหรับจ่ายเกินขั้นต่ำ ถ้าตั้ง "ปลดหนี้" เป็นเป้าหมาย เงินจะไปกองในซองออม ไม่ได้ลดยอดหนี้จริง

### กฎ 4: Goal Prioritization

**Implemented**
- `priority` (1 สำคัญสุด) ถ่วงน้ำหนักแบบลดหลั่น และ `deadline` กำหนดความเร็วที่ต้องออม
- ไม่แบ่งเท่ากัน: เงินไหลตามน้ำหนักและ deadline

**Missing**
- ไม่มีข้อมูล flexibility ของเป้า, ผลของการเลื่อน และประเภทเป้า (จำเป็น, การศึกษา, งาน, ไลฟ์สไตล์)
- deadline ทุกเป้าเป็นแบบ "พลาดได้แต่มีต้นทุน" ยังกำหนดเป้าที่ "ห้ามพลาด" ไม่ได้

**ข้อสังเกตที่ควรรู้**
- objective เป็นเชิงเส้น เงินจึงไหลเข้าเป้าที่น้ำหนักสูงก่อนจนเต็ม ไม่กระจาย เมื่อรายได้ลด 20% แผน Balanced ให้ Vacation **0 บาทจนถึง deadline** (ขาดเต็ม 15,000) ซึ่งตรงกับ "ไม่แบ่งเท่ากัน" แต่ทีมควรยืนยันว่าต้องการแบบนี้
- เป้าที่ไม่มี deadline ถูกตั้งให้ครบตอนสิ้น horizon ผลจึงขึ้นกับ horizon ที่เลือก (horizon 6 เดือนออม laptop 5,000 ต่อเดือน, 12 เดือนออม 5,416)

### กฎ 5: Allocation Constraints (Implemented)

- รวมการจัดสรรไม่เกินเงินที่มี: ตรวจระดับรายวัน ไม่ใช่แค่รายเดือน
- ไม่ติดลบ และไม่เกินยอดที่เป้ายังขาด
- เมื่อให้ทุนครบทุกเป้าไม่ได้ ระบบยังออกแผนที่เป็นไปได้ พร้อมระบุเป้าที่ไม่ทัน deadline และยอดที่ขาด ณ deadline
- `validate_plan` ตรวจทุกแผนซ้ำก่อนส่งออก และมี test กับโปรไฟล์สุ่ม 40 ชุด

จุดที่ยังขาดเล็กน้อย: เป้าที่ไม่ครบใน horizon รายงานว่า "ไม่ครบภายใน horizon" ยังไม่บอกว่า "ช้าไปกี่เดือน"

### กฎ 6: Financial Shocks

| Scenario | สถานะ | รายละเอียด |
|---|---|---|
| รายได้ลด 20% | Implemented | tool `simulate_income_change` และ slider ในแอป คำนวณแผนใหม่และอธิบายผล ทำบนสำเนา ไม่แตะข้อมูลจริง |
| ค่าใช้จ่ายไม่คาดคิด | Partially Implemented (อัปเดต 14 ต.ค. หลังรีวิว) | เพิ่ม tool `simulate_unexpected_expense` สำหรับจำลองแบบสมมติ: แสดงผลต่อแผนเดิมและแผนใหม่ที่จ่ายจากรายได้และเงิน unallocated เท่านั้น **ยังไม่มี** กลไกดึงเงินสำรองมาใช้และแผนฟื้นตัว (M5) ซึ่งรอกติกาจากทีมเศรษฐศาสตร์ |
| Deadline ใกล้เข้ามา | Partially Implemented | optimizer รองรับแล้ว ลองเลื่อน deadline ของ laptop เป็น 2 เดือน: ทุกแผนแจ้งว่าไม่ทัน ขาด 9,000 (Goal First), 14,667 (Balanced), 22,000 (Safety First) แต่ยังไม่มี scenario, test และการแจ้งเตือน |

ยังขาดทั้งสามกรณี: การอธิบาย **"อะไรเปลี่ยนไปจากแผนเดิม"** ตอนนี้แสดงแผนใหม่ แต่ไม่ได้เทียบส่วนต่างกับแผนก่อนเกิด shock

### กฎ 7: Explainability

**Implemented**
- ตัวเลขทุกตัวมาจาก engine คำอธิบายแบบ offline ประกอบจากผลของ tool โดยตรง
- คำตอบจาก LLM ถูกตรวจ ถ้ามีตัวเลขที่ไม่ได้มาจาก tool จะถูกทิ้งและแสดงคำอธิบายจาก engine แทน
- อธิบายการจัดสรรที่เสนอ, เป้าที่เลื่อน และ trade-off ระหว่างแผน

**Missing**
- ยังไม่แสดง available funds ในคำอธิบายแผน (ผูกกับกฎ 1)
- บอกได้ว่า "เป้าไหนช้า ขาดเท่าไร" แต่ยังไม่บอก "ทำไม" เช่น "เพราะ priority ต่ำกว่า laptop และเงินเหลือเดือนละ 5,000"

## 3. Needs Economics Decision

ข้อที่ต้องให้ทีมเศรษฐศาสตร์ตัดสิน ค่าแนะนำของผมเป็นเพียงจุดเริ่มต้น

| # | คำถาม | ทางเลือก | ค่าแนะนำ |
|---|---|---|---|
| D1 | Flexible spending ถือว่าคงที่ (หักก่อนแล้วค่อยจัดสรร) หรือตัดได้ | ก. คงที่ตามกฎ 1 ข. ตัดได้ถึงขั้นต่ำเหมือนปัจจุบัน | ข. แต่ต้องแจ้ง deficit ของงบเดิมให้เห็นก่อนเสมอ |
| D2 | เมื่องบเดิมติดลบแต่ตัด flexible แล้วพอ ให้ทำอย่างไร | ก. แจ้ง deficit และไม่ออกแผน ข. แจ้ง deficit และเสนอแผนที่ตัด flexible | ข. |
| D3 | ควรเก็บ buffer เงินสดขั้นต่ำที่ไม่นำไปจัดสรรไหม เท่าไร | ไม่มี, จำนวนคงที่, หรือสัดส่วนของค่าใช้จ่ายจำเป็น | ต้องการคำตอบจากทีม |
| D4 | เป้าเงินสำรอง: ฐานคำนวณรวมหนี้ขั้นต่ำไหม และผู้ใช้ตั้งค่าเองทับได้ไหม | 3 × จำเป็น หรือ 3 × (จำเป็น + หนี้ขั้นต่ำ) | รวมหนี้ขั้นต่ำ และให้ตั้งทับได้ |
| D5 | ดอกเบี้ยหนี้: คิดแบบไหน | ไม่คิด, ทบต้นรายเดือนที่ APR/12 | ทบต้นรายเดือน |
| D6 | จ่ายหนี้เพิ่ม: เรียงลำดับอย่างไร และต้องมีเงินสำรองเท่าไรก่อนเริ่มจ่ายเพิ่ม | APR สูงก่อน, ยอดน้อยก่อน | ต้องการคำตอบจากทีม |
| D7 | คุณสมบัติของเป้า: ประเภทมีอะไรบ้าง แต่ละประเภทคูณน้ำหนักเท่าไร และประเภทไหนเป็น deadline ห้ามพลาด | | ต้องการคำตอบจากทีม |
| D8 | เป้า priority ต่ำควรได้เงินขั้นต่ำบ้างไหม หรือยอมให้ได้ 0 เมื่อเงินตึง | ได้ 0 ได้, หรือกำหนดขั้นต่ำ | ต้องการคำตอบจากทีม |
| D9 | เป้าที่ไม่มี deadline ควรออมเร็วแค่ไหน | ครบสิ้น horizon (ปัจจุบัน), ระยะเวลาคงที่, หรือได้เฉพาะเงินเหลือ | ได้เฉพาะเงินเหลือหลังเป้าที่มี deadline |

ค่าที่ยังเป็นร่างและรอทีมยืนยันอยู่แล้ว: น้ำหนักทั้งหมดใน `config/strategy_weights.yaml`

| C3 | ใช้ horizon เดียวกันในคำอธิบาย shock และรายงานยอดขาดตัวเดียว (แก้ B2) | `agents/tools.py` | ไม่ต้องรอ |
| C4 | เพิ่ม buffer ขั้นต่ำเป็น constraint หนึ่งบรรทัดใน LP | `optimization/optimizer.py` | D3 |
| C5 | คิดดอกเบี้ยหนี้ใน forecast และเพิ่มตัวแปรจ่ายหนี้เพิ่มใน LP โดยให้น้ำหนักตาม APR | `cashflow/forecast.py`, `optimization/optimizer.py` | D5, D6 |
| C6 | เพิ่มฟิลด์ `category` และ `hard_deadline` ใน Goal ซึ่งป้อนเข้าน้ำหนักและ constraint | `domain/models.py`, `optimization/` | D7, D8 |
| C7 | เปลี่ยนวิธีจัดการเป้าไม่มี deadline (แก้ B5) | `optimization/optimizer.py` | D9 |
| C8 | เพิ่ม "เหตุผล" ในแผน: constraint ที่ตึง และลำดับน้ำหนักที่ทำให้เป้าถูกเลื่อน และเพิ่มการเทียบแผนก่อนกับหลัง shock | `optimization/plan.py`, `agents/explain.py` | ไม่ต้องรอ |
| C9 | ค่าใช้จ่ายไม่คาดคิด และการดึงเงินสำรอง (M4, M5) | package ใหม่ `shockproof/`, `recovery/` | D3 และกติกาการใช้เงินสำรอง |
| C10 | อนุมัติ, sandbox execution, audit log, กันทำซ้ำ (M3) | package ใหม่ `services/`, `sandbox/`, `database/` | ไม่ต้องรอ |

C3, C8 และ C10 ไม่ขึ้นกับการตัดสินใจทางเศรษฐศาสตร์ ทำได้ทันทีเมื่อทีมตกลง

## 6. Test ที่ควรรัน

**Scenario คำนวณมือที่ขอจากทีมเศรษฐศาสตร์** (ใช้แม่แบบใน `docs/team/templates/`)
